# Legacy v1: локальная диагностика Worker на Windows

Эта инструкция относится к legacy v1 helper, не к первичному подключению native v2. Для уже спаренного native Worker используйте [обзор](README.md) и [инструкцию переносимого пакета](portable/README.ru.md).

**Не останавливайте, не обновляйте и не перезапускайте единственный удалённый канал без проверенного независимого восстановления или локального оператора.** Ни этот helper, ни передача архива через Worker такого восстановления не обеспечивают.

## Помощник

В отдельном ZIP лежат рядом `worker-setup.cmd`, `worker-setup.mjs` и `relay-diagnose.mjs`. Node уже поставляется с DSH; launcher сначала ищет встроенный Node, затем PATH. Никаких npm-пакетов, прав администратора или смены PowerShell ExecutionPolicy не требуется.

1. Распаковать ZIP в отдельную папку на рабочем ПК.
2. Запустить `worker-setup.cmd` двойным щелчком и указать полный путь к существующему Worker JSON. Можно положить копию конфигурации рядом с помощником под именем `worker.json`, но не переносить существующий конфиг без учёта относительного stateDir.
3. Если папки проекта нет, подтвердить её создание буквой `y`.
4. Дождаться итогового `Validation: OK`. В отчёте нет ключей или токенов, но он может содержать локальный путь: перед отправкой оценить, допустимо ли его раскрывать.
5. Скопировать напечатанный полный путь в `settingsFile` плагина DSH и вручную выполнить `/remote-reload`. Это единственное действие с профилем, которое помощник намеренно не выполняет. Если вкладка содержит старый Client, обновить её.

Альтернативный запуск из PowerShell в папке помощника:

```powershell
.\worker-setup.cmd --config "C:\путь\worker.json" --create-project
```

Только проверка без изменения файлов:

```powershell
.\worker-setup.cmd --config "C:\путь\worker.json" --check
```

Без сетевых запросов: добавить `--no-network`.

## Что он делает и чего не делает

- Проверяет role, парные IDs, HTTPS URL, формат ключа и токена, проекты, пути и ограничения инструментов.
- Исправляет очевидный одиночный Windows-backslash в cwd/stateDir (включая случай `\r`), а также UTF-8 BOM. Корректные JSON-экранирования сохраняются; неоднозначные смешанные пути и произвольный повреждённый JSON отвергаются.
- Перед исправлением создаёт эксклюзивную timestamp-резервную копию. Она содержит секреты: не отправлять её в чат/репозиторий и не размещать в общей папке.
- Проверяет `/health` и авторизацию через **пустой ACK `{ids:[]}`**. Это не подтверждает никакие настоящие сообщения и не запускает задачи.
- Не меняет ключи, id/peerId, stateDir по смыслу, журналы, locks, профиль DSH, права, exportFinalText или allowedTools; не включает shell и не публикует код.
- Не считает HTTP200 health доказательством работы long-poll или native-сессии. После этого нужен тест 17×19 на Worker.
- Если файл находится под symlink/junction, или при проверке он был изменён другим процессом, ремонт прекращается.

Исправления небольшие и сохраняются с fsync и резервной копией, но это не обещание устойчивости редактирования к физическому отключению питания. Конфиг лучше исправлять до загрузки Worker, затем перечитать его через DSH.

## Relay и Tuna после закрытия SSH

Запущенные прямо в SSH-терминале процессы могут завершиться при разрыве сессии. Для теста используйте две tmux-сессии (tmux должен быть установлен). Не запускайте вторую копию поверх уже работающего relay на порту8787.

Первая SSH-вкладка:

```sh
tmux new -s dsh-relay
cd ~/dsh-remote-control
node relay/cli.mjs ./relay.json
```

Отключиться от tmux, НЕ останавливая relay: нажать Ctrl+B, затем D.

Вторая tmux-сессия:

```sh
tmux new -s dsh-tuna
tuna http 8787 --subdomain=YOUR_RESERVED_NAME --location=YOUR_REGION --https-redirect --inspect=false
```

Можно использовать уже проверенную вами команду Tuna, сохранив тот же постоянный HTTPS-адрес. Снова Ctrl+B, затем D. Теперь SSH можно закрыть. Логи смотрят через `tmux attach -t dsh-relay` и `tmux attach -t dsh-tuna`. После перезагрузки VPS эти сессии не восстановятся: для постоянного режима нужны systemd-службы.

## Разделение ошибок сети

- 401/403: токен или grant не соответствует конфигу relay.
- 502/503/504: ошибка посредника/его upstream либо недоступность relay; это не ошибка JSON cwd и не доказательство неверного ключа шифрования.
- 409 poll_already_active: другой экземпляр с тем же device ID уже опрашивает relay.
- Таймаут: DNS/TLS/сеть/туннель не ответили вовремя; секреты и сертификаты не отключать ради обхода.
- health200 + auth200 + poll502: отдельно проверить ожидание ответа через Tuna, локальный relay и логи. Для ограниченного теста можно добавить `"pollMs": 0` в relay-конфигурацию, сохранив остальные поля, и перезапустить relay. Это временный короткий опрос (больше HTTP-запросов), не готовый production-режим.

Дополнительная диагностика на конечном ПК с Node:

```sh
node relay-diagnose.mjs --config /path/to/endpoint.json
```

`--poll` использовать только когда обычный плагин на ЭТОМ устройстве остановлен: иначе диагностический запрос сам вызовет409. Диагностика не ACK-ает полученные poll-сообщения и не запускает native-задачи. Не копировать endpoint-конфиги с секретами на VPS ради этой проверки.

В выпуске плагина0.1.3 статус содержит `connection`, `lastSuccessfulPollAt`, `lastPollError`, а историческая `lastError` дополнена `httpStatus` и `route`. Историческую ошибку не нужно путать с текущим состоянием соединения.
