# Remote Control для DeepSeek Harness

Удалённые **native-сессии DSH**: Controller показывает источники и отправляет разрешённые операции; Worker выполняет их штатными SDK-сервисами на своей машине. Оба узла устанавливают исходящие соединения с relay. Relay передаёт зашифрованные сообщения; публичный DSH API, SSH и RDP не являются частью этого протокола.

## Исходники и готовые поставки

- Корневой пакет `@local/dsh-remote-control` сохраняет версию **0.1.5** и legacy-интерфейс v1. Его установка из этого каталога **не устанавливает** весь новый native Controller/Worker.
- Native-архитектура описана в [FEDERATION-V2.md](FEDERATION-V2.md), регистрация проектов — в [PROJECT-REGISTRATION-V1.md](PROJECT-REGISTRATION-V1.md), транспорт — в [TRANSPORT.md](TRANSPORT.md).
- Совместимый runtime — **DSH 0.2.2-rc.1**; native Worker требует Node.js **24.9+**. Проверяйте точные версии и зависимости в манифесте выбранного архива, не выдавайте version exemptions.
- Готовые Controller/Bridge/Worker-архивы распространяются отдельно через [Releases](https://github.com/NonEstSpes/dsh-plugins-public/releases). Наличие исходников не означает, что нужный архив уже опубликован или установлен. Проверяйте состав и контрольные суммы конкретного релиза.

**Ограничение воспроизводимости:** сборщики native Controller и Worker требуют отдельную модифицированную исходную копию `dsh-remote-core`, её зависимости и промежуточные артефакты. Эта копия **не включена в данный репозиторий**. Клонирования этого репозитория недостаточно для полной native-сборки или SDK/Loader acceptance-тестов; см. [заметки сборщиков](plugin-native/README.md). Копировать установленный SDK/ASAR в репозиторий не требуется.

## Обновление уже спаренного Worker v2

> **Не обновляйте, не выключайте и не перезапускайте единственный рабочий канал удалённого доступа без заранее проверенного независимого способа восстановления.** Если доступен только этот Worker, остановитесь: нужен локальный оператор или другой согласованный и проверенный канал. Передача архива через работающий Worker сама по себе не обеспечивает восстановление.

1. Проверьте совместимость архива с установленным DSH и существующим **Worker-конфигом версии 2**. Переносимый пакет не устанавливает DSH/Node.js и не создаёт новую пару.
2. Сохраните локальную защищённую резервную копию конфигурации пары, полного приватного состояния и native-данных. Не меняйте identities, ключи, grants или адрес relay ради обновления. Не отправляйте настройки, backup, cookies или журналы в чат/репозиторий.
3. На самом Worker выполните согласованное обслуживание через публичный Plugin Manager по [инструкции переносимого пакета](portable/README.ru.md). Не заменяйте signed EXE/ASAR, не правьте профиль вручную и не переключайте core/UI owners горячим способом. Сохраните прежний proxy-launcher, DPAPI, CA и независимый путь отката.
4. Указатель `settingsFile` должен ссылаться на **существующий локальный Worker v2 config**, не на Controller config. Роль создаётся явно; архив не подставляет фиктивный путь и не включает bridge скрыто.
5. После согласованного запуска прежним способом проверьте версии, единственного Worker API/Bridge owner и свежий аутентифицированный ответ. Отдельный короткий native-сценарий подтверждает работоспособность; установка, health и совпадение хешей этого не доказывают.

Старый binary не читает endpoint-state revision 2: откат требует совместимого backup/recovery, а не удаления replay-записей или ручной смены версии. См. [UPGRADE.md](UPGRADE.md).

**Первичное подключение не автоматизировано.** Здесь нет one-click мастера нового native-устройства или готового native pairing CLI. [scripts/pair.mjs](scripts/pair.mjs) — генератор **legacy v1**, не установщик native v2 и не способ обновить существующую пару. Не запускайте его для замены работающих credentials.

## Границы безопасности и поддержки

- Grants, текущая авторизация, native ownership и sandbox/approval policy проверяются на Worker; отчёт удалённой модели не является одобрением действия. Не обходите approvals, корпоративный proxy или TLS-проверки.
- Неизвестный исход операции остаётся unknown: не повторяйте её с новым request ID, не очищайте журналы/locks и не присваивайте существующие сессии по похожему пути.
- Загрузка вложений требует **уже live** native Agent; холодная сессия ради upload не активируется. Скачивание разрешается по точной ссылке в native пользовательском журнале, не по draft-квитанции и не как произвольный файловый доступ.
- Новый проект и экспорт файлов/изображений требуют явных текущих grants. Автоматического Git sync, публикации и удалённых approvals нет.
- HTTPS — default; WSS opt-in и его сроки подключения описаны в [TRANSPORT.md](TRANSPORT.md). Relay видит маршрутизацию и транспортную авторизацию, но не plaintext JWE. Отказ в обслуживании всё ещё возможен.
- Unit/loopback/native SDK proofs не подтверждают вашу физическую машину, WAN/TLS-туннель, power-loss, Windows ACL или визуальную работу установленной GUI. [Измерения](TRANSPORT-MEASUREMENTS.md) — одиночные локальные наблюдения, не гарантия производительности.

Legacy-формат и вспомогательные скрипты описаны в [PROTOCOL.md](PROTOCOL.md), [COMPATIBILITY.md](COMPATIBILITY.md) и [WORKER-SETUP.md](WORKER-SETUP.md). Операционные скрипты не запускаются автоматически. VPS helper требует явные `--url`, `--tuna-bin` и `--tuna-env`; адресов работающего развёртывания по умолчанию нет.
